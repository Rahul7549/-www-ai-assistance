Section 01

System Architecture

The voice chat is a full-duplex conversation loop between the user's browser and a locally-hosted Ollama LLM. The browser handles all speech processing (STT and TTS) via native Web Speech APIs, while the backend handles LLM inference and message persistence.

Browser (localhost:3000)                     Server (localhost:3001)
┌──────────────────────┐                    ┌──────────────────────┐
│  VoiceOverlay (UI)   │                    │  Socket.IO server    │
│    ↕                 │                    │    ↕                 │
│  useVoiceSession     │   Socket.IO ws     │  socket.ts handlers  │
│    ↕                 │ ←──────────────→   │    ↕                 │
│  VoiceSession class  │                    │  ChatService         │
│    ↕         ↕       │                    │    ↕          ↕      │
│  Web Speech  Web     │                    │  Ollama     Prisma   │
│  API         Audio   │                    │  (llama3)   (Postgres)│
│  (STT+TTS)   API    │                    │             ↕        │
│              (viz)   │                    │          MessageRepo  │
└──────────────────────┘                    └──────────────────────┘
Key design decision: All speech processing happens client-side using the Web Speech API — no audio is sent to the server. This keeps latency low and avoids transcription costs, at the cost of browser-dependent STT accuracy.

Section 03

Voice State Machine

The VoiceSession class manages a finite state machine with six states. All UI rendering and behavior branching derives from this single state property.

States

IDLE → LISTENING → PROCESSING → SPEAKING → LISTENING (loop)
LISTENING ⇄ MUTED ERROR ← any state

Transition triggers

IDLE → LISTENING       start() called, mic permission granted
LISTENING → PROCESSING  silence timer fires with final transcript
PROCESSING → SPEAKING   first TTS utterance starts playing
SPEAKING → LISTENING    last utterance finishes + stream is done
LISTENING ⇄ MUTED       toggleMute() called
any → ERROR             mic denied, socket error, AI error
any → IDLE              stop() called (overlay closed)
Section 04

Startup & Warm-up Flow

When the user opens the voice overlay, two parallel operations begin: the browser requests mic access, and the server pre-loads the Ollama model into memory.

  1. User clicks mic button → VoiceOverlay mounts
    The mount effect calls voiceRef.current.start() which triggers two parallel operations.
    VoiceOverlay.tsx:67-72
  2. Hook emits warm_model via Socket.IO
    Before calling session.start(), the hook emits warm_model to the backend. The session sets isWarmingUp = true and transitions to LISTENING.
    useVoiceSession.ts:210-212
  3. Browser requests getUserMedia
    VoiceSession.start() calls navigator.mediaDevices.getUserMedia({ audio: true }). Uses AbortController to handle React 19 StrictMode double-mount safely.
    VoiceSession.ts:370-404
  4. Audio analyser set up
    On mic grant, setupAnalyser(stream) creates an AudioContext + AnalyserNode for real-time volume visualization. State moves to LISTENING.
    VoiceSession.ts:257-291
  5. Backend warms Ollama model
    Server-side handler calls warmModel() — runs a minimal inference ("hi") to load model weights into RAM. Uses the singleton getVoiceModel() instance.
    socket.ts:36-39 → ChatService.ts:43-45
  6. Server emits model_ready
    Once warm completes, server emits model_ready. Client's modelReady() sets isWarmingUp = false and starts SpeechRecognition if not already running.
    VoiceSession.ts:458-464
  7. UI shows "Speak now"
    Overlay transitions from "Preparing assistant..." to "Speak now" — microphone is hot and STT is active.
Cold start elimination: The server also pre-warms the model on boot and sends a keepalive inference every 4 minutes, so subsequent voice sessions skip the ~14s cold load entirely.
Section 05

Conversation Turn Flow

Each voice turn follows this cycle: listen → detect silence → send to LLM → stream tokens → speak sentences as they arrive → return to listening.

  1. STT captures speech
    Web Speech API fires onresult events continuously. Interim results update the transcript in real-time; final results accumulate in finalText.
  2. Silence timer fires
    Each speech event resets a silence timer. Timeout is adaptive: 800ms for follow-up turns (conversation has context), 1200ms for the opening turn. When it fires, onFinalTranscript is called.
  3. Hook creates conversation if needed
    If no conversationId exists, the hook POSTs to /api/conversations to create one, then stores the ID in a ref for subsequent turns.
  4. Hook emits user_message via Socket.IO
    Message payload: { conversationId, content, mode: "voice" }. Records turnStartRef timestamp for metrics. Session transitions to PROCESSING.
  5. Backend saves user message + fetches context
    In parallel: saves user message to DB and fetches assistant details. Then loads the 6 most recent messages (desc query + reverse) for voice history context.
  6. Ollama streams tokens
    ChatOllama streams response with numPredict: 120 limit. Tokens batch in an 80ms buffer before Socket.IO emission. Voice system prompt enforces 1-3 sentence brevity.
  7. Client receives batched tokens → incremental TTS
    addToken() accumulates text, checks for sentence boundaries (/[.!?\n]\s*/). Each complete sentence is immediately queued to speechSynthesis.speak().
  8. Stream completes → speak remainder
    handleDone() sets streamDone = true, speaks any remaining text. A 10s safety timer ensures return to LISTENING even if TTS callbacks fail.
  9. Last utterance ends → return to LISTENING
    utt.onend checks streamDone && !speechSynthesis.pending. If both true, calls returnToListening() which clears transcript and restarts STT.
Section 06

Socket.IO Event Protocol

All voice communication uses a persistent WebSocket connection authenticated via JWT. The token is passed in socket.handshake.auth.token on connect.

Event Direction Payload Purpose
warm_model client → server none Request model pre-load into Ollama RAM
model_ready server → client none Acknowledge model is warm and ready
user_message client → server { conversationId, content, mode? } Send user's transcribed speech for LLM processing
ai_token server → client { token } Batched LLM output tokens (flushed every 80ms)
ai_done server → client { conversationId, content } Stream complete — full response included as fallback
ai_error server → client { message } Error during LLM inference or DB access
cancel_stream client → server none Abort ongoing inference (AbortController signal)
Section 07

Speech-to-Text (STT)

STT uses the browser's native SpeechRecognition API (Chrome/Edge). It runs in continuous mode with interim results enabled for real-time transcript display.

Configuration

rec.lang = "en-US"
rec.continuous = true       // don't stop after one phrase
rec.interimResults = true   // show partial results while speaking

Transcript handling

The onresult handler separates final (committed) from interim (tentative) text. Final text accumulates in finalText; the combined transcript is displayed in the UI. When the browser marks a result as isFinal, it's locked — interim text continues to update independently.

Auto-restart

Chrome's SpeechRecognition stops after periods of silence. The onend handler automatically restarts recognition while in LISTENING state, making it appear continuous to the user.

Silence detection

A debounced timer triggers after speech stops. The timeout is adaptive:

const hasContext = !!this.aiResponse;   // has the AI spoken yet?
const timeout = hasContext ? 800 : 1200; // faster for follow-ups

When the timer fires, if finalText is non-empty and state is LISTENING, the transcript is sent for processing via the onFinalTranscript callback.

Section 08

Text-to-Speech (TTS)

TTS uses the browser's native SpeechSynthesis API. Rather than waiting for the full AI response, sentences are queued for speech as they're detected in the token stream — so the user hears speech while text is still arriving.

Incremental sentence detection

private static SENTENCE_END = /[.!?\n]\s*/;

addToken(token) {
  this.aiResponse += token;
  const unspoken = this.aiResponse.slice(this.spokenIndex);
  const match = VoiceSession.SENTENCE_END.exec(unspoken);
  if (match) {
    // extract sentence, advance spokenIndex, call speakSentence()
  }
}

The spokenIndex tracks how far into the response has been queued for speech. When addToken() detects a sentence boundary in the unspoken portion, it extracts the sentence and immediately queues it. The speechSynthesis queue handles ordering.

Voice selection

Three named voices are mapped to native system voices via keyword matching:

VOICE_MAP = {
  "Nova - Energetic & Fast":      // rate: 1.1
  "Echo - Soft & Calm":           // rate: 1.0
  "Atlas - Deep & Professional":  // rate: 1.0
}

Each maps to a prioritized keyword list (e.g., ["zira", "samantha", "karen", "female"]) matched against English-language voices available in the browser.

Turn completion

When handleDone() is called (stream complete), it sets streamDone = true and speaks any remaining text. The last utterance's onend checks streamDone && !speechSynthesis.pending — when both are true, the session transitions back to LISTENING.

Safety net: A 10-second timeout in handleDone() forces a return to LISTENING even if TTS onend callbacks never fire (a known browser edge case).
Section 09

Audio Visualization

Real-time microphone volume drives the animated orb and frequency bars in the overlay.

Pipeline

getUserMedia → MediaStreamSource → AnalyserNode (fftSize: 256)
                                        ↓
                              getByteTimeDomainData(dataArray)
                                        ↓
                                RMS volume (0–1)
                                        ↓
                           threshold filter (Δ > 0.02)
                                        ↓
                              throttledNotify() → React

The analyser runs on every requestAnimationFrame tick. It computes RMS (root mean square) from the time-domain waveform, then normalizes to 0–1 with a 3x multiplier for visual sensitivity.

Rendering

The overlay's animation clock also runs via requestAnimationFrame, but only when state is LISTENING or SPEAKING. The volume value drives:

// Orb scale
orbScale = 1 + volume * 0.4         // LISTENING: mic-reactive
orbScale = 1 + sin(now/200) * 0.15  // SPEAKING: gentle pulse

// Bar heights (15 bars per side)
height = 10 + volume * 40 + sin(now/150 + i * 0.5) * 10  // LISTENING
height = 10 + sin(now/200 + i * 0.4) * 25                // SPEAKING
Section 10

React Integration Pattern

The voice pipeline uses an imperative class + snapshot pattern to avoid common React pitfalls with browser APIs.

Why not plain hooks?

Browser APIs like SpeechRecognition, AudioContext, and MediaStream are imperative, long-lived, and stateful. Putting them in hooks leads to stale closures, effect dependency churn, and React 19 StrictMode double-mount race conditions. The class pattern solves all three.

The pattern

// 1. Class owns all browser API state (no React dependency)
class VoiceSession {
  state: VoiceState = "IDLE";
  onChange: (() => void) | null = null;   // callback to React
  // ... browser API instances as private fields
}

// 2. Hook creates class once via lazy-ref init
const sessionRef = useRef<VoiceSession | null>(null);
if (sessionRef.current == null) {
  sessionRef.current = new VoiceSession();
}

// 3. Snapshot for rendering — never read ref during render
const [snap, setSnap] = useState<Snapshot>(() => ({ ... }));

// 4. Wire onChange in effect — safe ref access
useEffect(() => {
  const s = sessionRef.current!;
  s.onChange = () => setSnap(takeSnapshot(s));
  return () => { s.onChange = null; };
}, []);

// 5. Methods in useCallback — ref access inside callbacks
const start = useCallback(() => {
  sessionRef.current?.start();
}, []);
React 19 lint compliance: The == null lazy-ref pattern satisfies react-hooks/refs (no ref access during render). Snapshot state satisfies react-hooks/immutability (no direct class mutation visible to React render).

StrictMode safety

React 19 StrictMode double-invokes effects in development. The start() method uses an AbortController — the second mount aborts the first's getUserMedia call and stops its mic tracks, preventing resource leaks.

Section 11

Backend Streaming Pipeline

Model management

Voice mode uses a singleton ChatOllama instance shared between warm-up and inference:

let voiceModel: ChatOllama | null = null;

function getVoiceModel(): ChatOllama {
  if (!voiceModel) {
    voiceModel = new ChatOllama({
      model: "llama3",        // 8B Q4_0, ~3.6 tokens/sec on CPU
      temperature: 0.7,
      numPredict: 120,        // voice response length cap
    });
  }
  return voiceModel;
}

Text chat mode still creates a fresh ChatOllama via createChatModel() (no numPredict cap).

Voice system prompt

Voice mode appends a behavioral constraint to the assistant's personality prompt:

"You are in a live voice conversation. Keep responses brief —
1 to 3 sentences max. Be direct and conversational. Do not
use markdown, bullet points, or formatting."

Message history

Voice mode fetches the 6 most recent messages using findRecentByConversationId — a desc query reversed in code, ensuring the latest conversation context (not the oldest). Text chat uses the standard ascending query with a 20-message limit.

Database call pattern

// Sequential: conversation lookup (need assistantId first)
const conversation = await conversationRepo.findById(conversationId);

// Parallel: assistant lookup + user message save (independent)
const [assistant] = await Promise.all([
  assistantRepo.findById(conversation.assistantId),
  messageRepo.create({ conversationId, role: "USER", content }),
]);

// Then: load history
const history = await messageRepo.findRecentByConversationId(...);

Token streaming & batching

The LLM stream yields tokens one at a time. Instead of emitting each token as a separate Socket.IO event (high overhead at ~3.6 tok/s), tokens accumulate in a buffer and flush every 80ms:

let tokenBuf: string[] = [];
let flushTimer = null;

onToken: (token) => {
  tokenBuf.push(token);
  if (!flushTimer) {
    flushTimer = setTimeout(flushTokens, 80);
  }
}

On stream completion (onDone) or error, the buffer is force-flushed before emitting the terminal event.

Section 12

Performance Optimizations

Nine targeted optimizations reduce perceived latency and render load without changing the core architecture.

1
Singleton voice model
Reuses one ChatOllama instance for both warmModel() and streamChat(), avoiding re-instantiation overhead on every call.
ChatService.ts — getVoiceModel()
2
Parallel DB calls
Assistant lookup and user message creation run in Promise.all() — independent operations that previously ran sequentially.
ChatService.ts:65-68
3
Correct history direction
Voice history uses ORDER BY createdAt DESC + reverse, fetching the latest N messages instead of the oldest N (which could miss recent context).
MessageRepository.ts — findRecentByConversationId()
4
Token batching + notify throttle
Backend: tokens buffer for 80ms before socket emission. Frontend: throttledNotify() coalesces rapid state changes into ~50ms render frames.
socket.ts (backend) + VoiceSession.ts (frontend)
5
Server-boot warm + keepalive
Model pre-warms on initSocket() and stays warm via a 4-minute keepalive interval, eliminating cold starts entirely for the user.
socket.ts:13-14
6
Adaptive silence timeout
Follow-up turns use 800ms silence threshold (user expects fast turns); the first turn uses 1200ms (user may pause to think).
VoiceSession.ts — resetSilenceTimer()
7
handleDone hang fix
A 10-second safety timer forces return to LISTENING if TTS onend callbacks never fire — prevents the UI from getting stuck in SPEAKING state.
VoiceSession.ts — handleDone()
8
Volume change threshold
Skips React re-renders when volume change is below 0.02 — eliminates ~60% of analyser-driven renders that produce no visible change.
VoiceSession.ts — setupAnalyser() tick loop
9
Metrics instrumentation
Backend logs TTFT, total time, tokens/sec. Frontend logs client-TTFT and turn-duration. All prefixed [voice-metrics] for easy filtering.
ChatService.ts + useVoiceSession.ts
