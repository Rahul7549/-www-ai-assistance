01

High-Level Architecture & Design Rationale

The voice chat system is a real-time, full-duplex conversation loop between the browser and a locally-hosted LLM (Ollama running llama3 8B). The user speaks, the browser transcribes speech to text, sends the text to the server over a WebSocket, the server streams AI tokens back, and the browser reads them aloud sentence-by-sentence — all while showing live visual feedback.

Browser (Next.js, port 3000)                 Server (Express, port 3001)
┌────────────────────────┐                  ┌────────────────────────┐
│  VoiceOverlay  (UI)    │                  │  Socket.IO Server      │
│       ↕                │                  │       ↕                │
│  useVoiceSession (hook)│   WebSocket      │  Event Handlers        │
│       ↕                │ ←────────────→   │       ↕                │
│  VoiceSession  (class) │                  │  ChatService           │
│    ↕          ↕        │                  │    ↕          ↕        │
│  Web Speech   Web Audio│                  │  ChatOllama  Prisma    │
│  API          API      │                  │  (LangChain) (Postgres)│
│  (STT + TTS)  (volume) │                  │       ↕                │
└────────────────────────┘                  │  MessageRepository     │
                                            └────────────────────────┘

The most important architectural decision is that all speech processing happens entirely in the browser. The Web Speech API handles both speech-to-text (STT) and text-to-speech (TTS) natively — no audio data ever leaves the client. This was a deliberate trade-off: it eliminates network latency for transcription, avoids third-party API costs (Whisper, Google STT), and keeps the system self-contained, but it limits STT accuracy to what the browser provides (Chrome's engine is good but not perfect) and restricts voice chat to browsers that support the Web Speech API (Chrome and Edge).

The communication layer uses Socket.IO rather than REST because voice conversation is inherently bidirectional and streaming. The server needs to push tokens as they arrive from the LLM — polling or long-polling would add unacceptable latency. Socket.IO provides WebSocket transport with automatic reconnection, room-based routing, and a clean event-based API. The connection is authenticated using JWT tokens passed during the handshake.

The LLM runs locally via Ollama with the llama3 8B model (Q4_0 quantization). On CPU, this produces roughly 3.6 tokens per second. Voice mode constrains responses to 120 tokens maximum and appends a system prompt that enforces 1–3 sentence brevity — because a voice assistant that rambles for 30 seconds is unusable.

02

File Structure & Separation of Concerns

The codebase is split across two repositories. The frontend is a Next.js 16 application with React 19, and the backend is an Express server. Within the frontend, the voice system is organized into three layers, each with a single responsibility:

Frontend

app/_components/voice/VoiceSession.ts
Pure imperative class. Manages all browser APIs (SpeechRecognition, SpeechSynthesis, AudioContext, MediaStream). Contains the state machine. Has zero React imports — it's framework-agnostic.
app/_components/hooks/useVoiceSession.ts
Thin React bridge. Creates the VoiceSession once, wires its onChange callback to React state via snapshots, connects Socket.IO listeners, handles conversation creation.
app/_components/VoiceOverlay.tsx
Pure presentational component. Full-screen overlay with animated orb, frequency bars, transcript display, voice selector dropdown, and control buttons. Renders from the snapshot state.
app/lib/socket.ts
Socket.IO client singleton. Creates one connection per session, authenticated via JWT from localStorage. Provides getSocket(), reconnectSocket(), disconnectSocket().

Backend

src/config/socket.ts
Socket.IO server setup. JWT auth middleware, event handlers (warm_model, user_message, cancel_stream), token batching logic, model keepalive interval.
src/services/ChatService.ts
Core business logic. Singleton voice model management, system prompt construction with personality traits, LLM streaming with async iterators, message history, metrics instrumentation.
src/repositories/MessageRepository.ts
Prisma data access layer. Standard CRUD plus findRecentByConversationId — a descending query that returns the latest N messages in chronological order.
src/config/ai.ts
ChatOllama factory for text chat mode. Voice mode bypasses this and uses its own singleton instance with a numPredict cap.

This separation matters because each layer can be understood, tested, and modified independently. The VoiceSession class could be dropped into a vanilla JS app with zero changes. The React hook handles only the bridging concerns (state synchronization, socket wiring, conversation management). The overlay component is purely presentational — it receives data and renders it.

03

The Imperative Class Pattern (and why not hooks)

The voice feature manages several long-lived, stateful browser APIs simultaneously: SpeechRecognition (continuous microphone listening), SpeechSynthesis (a queue of utterances being spoken), AudioContext with an AnalyserNode (real-time volume), and a MediaStream (the mic track itself). These are imperative APIs — you call .start(), attach event handlers, and the objects persist and mutate over time.

The first implementation used React hooks directly: useRef for the SpeechRecognition instance, useEffect for setup/teardown, useState for the transcript. This caused three categories of bugs:

Stale closures. When a useEffect captures a callback at mount time, it closes over the state values from that render. If an onresult handler references a transcript state variable, it sees the value from the render when the effect ran — not the current value. Every speech event would overwrite previous text. The workaround is adding more refs, but that turns the hook into a ref-management nightmare.

Effect dependency churn. React hooks require listing all referenced variables in dependency arrays. With five browser APIs and a dozen state variables, the effect dependencies become unwieldy — and any missed dependency causes stale reads. Adding correct dependencies causes effects to re-run, tearing down and rebuilding SpeechRecognition on every state change.

React 19 StrictMode double-mount. In development, React 19 mounts every component twice (mount → unmount → mount) to expose side-effect bugs. With browser APIs, this means getUserMedia is called twice, two mic streams are opened, and the first one leaks because the teardown races with the second setup.

The solution is the imperative class + snapshot pattern. The VoiceSession class owns all browser API instances as private fields and exposes public properties (state, transcript, aiResponse, volume, etc.) that represent the current truth. It has a single onChange callback — when anything changes, it calls onChange() and the React hook takes a snapshot:

// The class — no React, no closures, no stale state
class VoiceSession {
  state: VoiceState = "IDLE";
  transcript = "";
  onChange: (() => void) | null = null;

  addToken(token: string) {
    this.aiResponse += token;       // direct mutation, always current
    this.throttledNotify();          // tell React to re-snapshot
  }
}

// The hook — creates class once, reads snapshots for rendering
const sessionRef = useRef(null);
if (sessionRef.current == null) {
  sessionRef.current = new VoiceSession();   // lazy-ref init
}

const [snap, setSnap] = useState(() => initialSnapshot);

useEffect(() => {
  const s = sessionRef.current!;
  s.onChange = () => setSnap(takeSnapshot(s));  // mirror class → state
  return () => { s.onChange = null; };
}, []);

This pattern satisfies React 19's strict lint rules: the == null lazy-ref init is the lint-approved way to initialize refs without triggering react-hooks/refs (which forbids reading .current during render). The snapshot state satisfies react-hooks/immutability (React never sees the mutable class directly — only frozen snapshots). And methods are wrapped in useCallback that access the ref inside the callback body, which is safe because callback execution happens outside render.

For StrictMode double-mount, the start() method uses an AbortController. When React unmounts the first instance, the cleanup calls abort(). The second mount creates a new controller. The first getUserMedia promise checks signal.aborted when it resolves — if the first mount was torn down, it stops the mic tracks immediately and returns. No resource leak.

04

Voice State Machine

The entire system's behavior is governed by a single state property on the VoiceSession class. There are six possible states, and all UI rendering, API behavior, and transition logic branches on this value.

IDLE → LISTENING → PROCESSING → SPEAKING → LISTENING (loop)

IDLE is the initial state — the overlay is not open, no resources are allocated. LISTENING means the mic is active and SpeechRecognition is running; the UI shows "Speak now" and the orb pulses with microphone volume. PROCESSING means the user's speech has been sent to the backend and we're waiting for (or receiving) AI tokens — the orb shows a thinking animation and streaming text appears in real-time. SPEAKING means TTS is actively reading the response aloud. MUTED pauses recognition while preserving the previous state for un-mute. ERROR captures any failure (mic denied, socket error, AI error) with a message and a retry button.

The key insight is the PROCESSING → SPEAKING overlap. Because TTS starts as soon as the first sentence boundary is detected in the token stream (not after the full response), the system transitions to SPEAKING while tokens are still arriving. The addToken() method works in both PROCESSING and SPEAKING states. This overlap is what makes the voice feel responsive — the user hears the first sentence within 2–3 seconds of the first token, while the rest of the response is still being generated.

The loop closes when the last TTS utterance finishes: the onend callback checks this.streamDone && !speechSynthesis.pending. If the stream is complete and no more utterances are queued, it calls returnToListening() — which clears the transcript, restarts SpeechRecognition, and sets state back to LISTENING. The user can immediately speak again.

05

Full Lifecycle: Startup to First Word

When the user taps the microphone button in the chat interface, the VoiceOverlay component mounts. Its mount effect triggers two parallel operations that must both complete before the user can speak:

Path A — Browser side: The hook's start() callback fires, which does two things. First, it emits a warm_model event to the server via Socket.IO. Second, it calls session.start() on the VoiceSession class. Inside start(), the class calls navigator.mediaDevices.getUserMedia({ audio: true }) to request microphone access. This is async and may show a browser permission dialog. While waiting, the class sets isWarmingUp = true and transitions to LISTENING — the UI shows "Preparing assistant..." so the user knows something is happening.

Once the mic stream is granted, setupAnalyser(stream) creates an AudioContext, pipes the mic stream through a MediaStreamSource into an AnalyserNode (FFT size 256), and starts a requestAnimationFrame loop that reads time-domain waveform data and computes RMS volume 60 times per second. This drives the orb animation immediately — the user sees visual feedback that the mic is working.

Path B — Server side: The warm_model handler on the server calls warmModel() in ChatService, which invokes the singleton ChatOllama instance with a trivial input ("hi"). For Ollama, the first inference after a cold start loads the entire model file (~4.3GB for llama3 8B Q4_0) into RAM. This takes about 14 seconds on a machine without GPU. Once warm completes, the server emits model_ready back to the client.

Convergence: When the client receives model_ready, the VoiceSession's modelReady() method sets isWarmingUp = false. If the state is LISTENING and SpeechRecognition hasn't started yet (mic was granted but we were waiting for the model), it now calls setupRecognition(). The UI transitions from "Preparing assistant..." to "Speak now" — both paths have completed and the system is fully ready.

Why gate recognition on model readiness? If STT starts immediately, the user might speak a full sentence before the model is loaded. The silence timer would fire, send the transcript to the backend, and the backend would block for 14 seconds while Ollama loads — with no feedback. By gating on model_ready, the user only sees "Speak now" when the system can actually respond quickly.
06

Full Lifecycle: A Complete Conversation Turn

Once the system is in LISTENING state, a single conversation turn flows through every layer of the stack. Here is exactly what happens from the moment the user finishes speaking to the moment they can speak again:

1. Speech capture and silence detection. The Web Speech API fires onresult events continuously as the user speaks. Each event contains an array of results — some marked isFinal (committed transcription), others interim (tentative, may change). The handler separates these and updates the live transcript displayed in the UI. Each speech event resets a silence timer. The timer uses adaptive timeouts: 1200ms for the first turn (user may pause to think), 800ms for follow-up turns (conversation is flowing, faster response expected). When the timer fires without new speech, it takes finalText (the committed transcription) and passes it to the onFinalTranscript callback.

2. Conversation creation and message dispatch. The onFinalTranscript callback lives in the React hook. It first checks if a conversation exists. If this is the first turn, it creates one via a REST POST to /api/conversations and stores the returned ID in a ref. Then it records a turnStartRef timestamp (for metrics), emits a user_message Socket.IO event with { conversationId, content, mode: "voice" }, and calls session.setProcessing() — which tears down SpeechRecognition (so it doesn't pick up its own TTS output), clears the transcript, resets token tracking, and moves to PROCESSING state.

3. Backend receives and processes. The socket handler validates the payload, creates an AbortController (for cancellation support), and calls streamChat(). Inside streamChat, the flow is: look up the conversation to get the assistantId → in parallel, fetch the assistant record and save the user message to the database → load the 6 most recent messages for voice context → construct the message array with a system prompt that includes the assistant's personality plus voice-mode brevity instructions → create a streaming inference call to the singleton ChatOllama instance.

4. Token streaming with batching. Ollama yields tokens one at a time through an async iterator. At ~3.6 tokens/sec, that's roughly one token every 280ms. Instead of emitting each token as a separate Socket.IO event (which would mean ~3.6 network frames per second with overhead), the socket handler uses a batching strategy: tokens accumulate in an array buffer, and a timer flushes them as a single concatenated string every 80ms. This reduces socket emissions by roughly 70% while keeping perceived latency under 80ms per batch.

5. Client-side token handling and incremental TTS. Each batched ai_token event calls session.addToken(batchedText). The method appends the text to aiResponse (which the UI renders immediately with a blinking cursor) and then checks for sentence boundaries using the regex /[.!?\n]\s*/. It maintains a spokenIndex — a pointer into aiResponse marking how far has been sent to TTS. When a sentence boundary is found in the unspoken portion, it extracts the sentence, advances spokenIndex, and calls speakSentence().

6. TTS queuing and playback. speakSentence() creates a SpeechSynthesisUtterance, sets the selected voice and rate, attaches onstart/onend/onerror handlers, and calls speechSynthesis.speak(utt). The browser's TTS engine queues multiple utterances — so while sentence 1 is being spoken, sentences 2 and 3 can already be queued. The onstart of the first utterance transitions to SPEAKING state. Each subsequent sentence just adds to the queue.

7. Stream completion. When the LLM finishes, the server force-flushes any remaining buffered tokens and emits ai_done with the full response as a fallback. The client calls session.handleDone(), which sets streamDone = true, speaks any remaining unspoken text, and starts a 10-second safety timer. The normal path: the last utterance's onend fires, sees streamDone && !speechSynthesis.pending, and calls returnToListening(). The safety timer is a fallback for the edge case where browser TTS callbacks silently fail.

8. Return to LISTENING. returnToListening() clears the transcript fields, restarts SpeechRecognition, sets state to LISTENING, and notifies React. The UI shows "Speak now" again. The user can immediately begin their next turn. The conversation loop continues.

07

Speech-to-Text Engine

STT uses the browser's native SpeechRecognition API (available as window.SpeechRecognition in Chrome and window.webkitSpeechRecognition in Edge). The API is configured for continuous listening with interim results:

const rec = new (window.SpeechRecognition || window.webkitSpeechRecognition)();
rec.lang = "en-US";
rec.continuous = true;        // don't stop after one phrase
rec.interimResults = true;    // show partial results while speaking

continuous: true is important because by default, SpeechRecognition stops after detecting a pause in speech — which would make it useless for a conversation. However, even in continuous mode, Chrome's implementation periodically stops the session internally (roughly every 60 seconds or after long silence). The onend handler detects this and automatically restarts recognition if the state is still LISTENING, making it appear seamless to the user.

The onresult handler receives a SpeechRecognitionResultList — an array of result objects. Each result has an isFinal flag: when true, the transcription is committed and won't change. When false, it's a live interim prediction that the browser may revise. The handler separates these into finalText (accumulated committed text) and interimTranscript (current tentative text). The combined transcript (final + interim) is displayed to the user in real-time. The UI styles interim text in italicized gray so the user can distinguish confirmed from tentative words.

Since TypeScript doesn't include SpeechRecognition types by default, the file declares global interfaces for SpeechRecognition, SpeechRecognitionEvent, SpeechRecognitionErrorEvent, and the corresponding Window properties. This provides full type safety without external type packages.

08

Text-to-Speech & Incremental Streaming

The most important UX decision in the entire voice system is incremental TTS — speaking each sentence as it arrives rather than waiting for the complete AI response. Without this, the user would wait for the entire LLM generation (potentially 30+ seconds at 3.6 tok/s) before hearing anything. With it, the user hears the first sentence within a few seconds of the first token.

The mechanism works through a spokenIndex pointer. As tokens arrive via addToken(), they're appended to aiResponse. The method then checks the unspoken portion (everything from spokenIndex to the end) for sentence boundaries using the regex /[.!?\n]\s*/. When a boundary is found, the sentence is extracted, spokenIndex advances past it, and speakSentence() is called. The browser's speechSynthesis.speak() method naturally queues multiple utterances, so sentences play back-to-back without gaps.

addToken(token: string) {
  if (this.state !== "PROCESSING" && this.state !== "SPEAKING") return;
  this.aiResponse += token;
  this.throttledNotify();        // update UI (shows streaming text)

  const unspoken = this.aiResponse.slice(this.spokenIndex);
  const match = VoiceSession.SENTENCE_END.exec(unspoken);
  if (match) {
    const boundary = this.spokenIndex + match.index + match[0].length;
    const sentence = this.aiResponse.slice(this.spokenIndex, boundary);
    this.spokenIndex = boundary;
    this.speakSentence(sentence, this.state === "PROCESSING");
  }
}

The isFirst parameter to speakSentence() controls whether to call speechSynthesis.cancel() and tear down recognition before speaking. On the first sentence, this ensures no stale audio is playing and stops the mic from picking up the TTS output (which would create a feedback loop). Subsequent sentences just queue without disruption.

Three named voice profiles are available — Nova (energetic, rate 1.1), Echo (soft, rate 1.0), and Atlas (deep, rate 1.0). Each maps to a prioritized list of keywords matched against the browser's available English voices (e.g., ["zira", "samantha", "karen", "female"]). The system falls back gracefully: if no keyword matches, it picks the first English voice; if no English voice exists, it picks the first voice available.

When the stream completes and handleDone() is called, any remaining unspoken text is flushed to TTS. The streamDone flag is set to true. The last utterance's onend callback checks this flag — if the stream is done and no more utterances are pending, the system transitions back to LISTENING.

Real-Time Audio Visualization

The voice overlay features a central orb that pulses with microphone volume and 30 frequency bars (15 per side) that animate with speech energy. This visualization serves an important UX purpose: it gives the user confidence that the microphone is actually working and hearing them.

The pipeline starts with the MediaStream from getUserMedia. This is connected to a Web Audio API graph: AudioContext → MediaStreamSource → AnalyserNode. The analyser is configured with fftSize: 256, which gives 128 frequency bins. On every requestAnimationFrame tick, getByteTimeDomainData() fills a Uint8Array with the current waveform. The handler computes RMS (root mean square) by squaring each sample's deviation from the center (128), averaging, and taking the square root. A 3x multiplier boosts visual sensitivity. The result is clamped to 0–1.

// Volume computation (runs at ~60fps)
analyserNode.getByteTimeDomainData(dataArray);
let sum = 0;
for (let i = 0; i < dataArray.length; i++) {
  const v = (dataArray[i] - 128) / 128;   // normalize to -1..1
  sum += v * v;                            // square
}
volume = Math.min(1, Math.sqrt(sum / dataArray.length) * 3);  // RMS × 3

A key optimization: the volume only triggers a React re-render if the change exceeds a threshold of 0.02. Without this, every animation frame would cause a re-render even when volume barely fluctuates — roughly 60 re-renders per second, most producing no visible change. The threshold eliminates about 60% of these wasted renders.

In the overlay component, the animation clock also runs via requestAnimationFrame, but only while state is LISTENING or SPEAKING. The volume drives two visual properties: the orb scales between 1.0 and 1.4 proportional to volume during LISTENING, and the frequency bars compute heights using a combination of volume amplitude and sine-wave offset (creating a wave effect across the bar array). During SPEAKING, both switch to time-based sine animations since the mic is off.

10

Socket.IO Transport Layer

The WebSocket connection is the bridge between the browser's speech pipeline and the server's LLM pipeline. It carries seven distinct event types:

EventDirectionPayloadWhen & Why
warm_modelclient → server—Emitted when overlay mounts. Triggers Ollama model load.
model_readyserver → client—Model weights are in RAM. Client enables STT and shows "Speak now."
user_messageclient → server{ conversationId, content, mode }User's transcribed speech. mode: "voice" enables brevity constraints.
ai_tokenserver → client{ token }Batched LLM tokens (flushed every 80ms, not per-token).
ai_doneserver → client{ conversationId, content }Stream complete. Full response included as fallback for missed tokens.
ai_errorserver → client{ message }Any failure — DB, Ollama, permission check.
cancel_streamclient → server—User closes overlay mid-stream. Triggers AbortController.abort().

The connection is authenticated via JWT. When the Socket.IO client is created, it passes auth: { token } in the handshake options. The server's io.use() middleware extracts and verifies this token before allowing the connection. The decoded payload (containing userid) is stored in socket.data.user and used to join the user's room and validate message ownership.

Each connected socket maintains a per-connection AbortController. If a new message arrives while inference is still running, or if the user disconnects, the controller's abort() signal propagates through the LLM stream loop, breaking the async iterator and cleaning up.

11

Backend: LLM Streaming Pipeline

The backend's streamChat() function is the core orchestration layer. It handles authentication, conversation context loading, prompt construction, streaming inference, message persistence, and metrics — all within a single async function that communicates progress through callbacks.

Model management

Voice mode uses a singleton ChatOllama instance — a module-level variable initialized on first access via getVoiceModel(). This is reused for both warm-up pings and actual inference. The singleton avoids re-instantiation overhead (connection setup, configuration parsing) on every call. Text chat mode uses a separate factory (createChatModel()) without a numPredict cap, since text responses can be longer.

Database access pattern

The function makes four database calls, optimized for minimal total latency. The conversation lookup must happen first because it provides the assistantId needed for the next query. But the assistant lookup and user message creation are independent — so they run in Promise.all(). Finally, message history is loaded. For voice mode, this uses findRecentByConversationId — which queries ORDER BY createdAt DESC LIMIT 6 and reverses the result in application code. This guarantees the 6 most recent messages regardless of total conversation length. The standard ascending query with LIMIT 20 would return the oldest 20 messages — wrong for voice context where only the recent exchange matters.

Prompt construction

Each assistant has a name and personality (PROFESSIONAL, FRIENDLY, WITTY, CONCISE, CREATIVE). The system prompt starts with identity rules that prevent the model from revealing its underlying architecture ("You are NOT LLaMA, NOT GPT..."). Voice mode appends: "You are in a live voice conversation. Keep responses brief — 1 to 3 sentences max. Be direct and conversational. Do not use markdown, bullet points, or formatting." This is critical because markdown symbols, asterisks, and bullet points are nonsensical when spoken aloud.

Streaming

The model.stream(messages) call returns an async iterable. The function iterates with for await, checking signal?.aborted on each chunk to support cancellation. Each chunk's content field is extracted and passed to the onToken callback, which the socket handler uses for batched emission.

After the stream completes, the full response is saved to the database as an ASSISTANT message. If this was the first message in the conversation, the conversation title is auto-generated from the user's message (truncated to 50 characters).

Cold Start Elimination Strategy

Ollama's cold start is the single biggest latency bottleneck. When the model isn't loaded in RAM, the first inference must read ~4.3GB from disk into memory — taking roughly 14 seconds on a machine with HDD storage. This is a catastrophic user experience for a voice assistant that's supposed to feel instant.

The system eliminates cold starts through a three-layer strategy:

Layer 1 — Server boot warm. When initSocket() runs at server startup, it immediately calls warmModel().catch(() => {}). This runs a trivial inference that forces Ollama to load the model. By the time any user connects, the model is already in RAM. The .catch() swallows errors silently — if Ollama isn't running yet, the keepalive (layer 2) will retry.

Layer 2 — Keepalive interval. A setInterval runs warmModel() every 4 minutes. Ollama unloads models after a configurable idle timeout (default 5 minutes). The keepalive fires before this timeout, keeping the model perpetually warm. The 4-minute interval provides a safety margin.

Layer 3 — On-demand warm. When the user opens the voice overlay, the client emits warm_model regardless. If the model is already warm (which it should be thanks to layers 1 and 2), this completes almost instantly and model_ready fires immediately. If something went wrong and the model was evicted, this is the fallback — the user sees "Preparing assistant..." for the duration of the reload.

Trade-off: The keepalive holds ~4.3GB of RAM permanently. On a machine with limited memory, this could be wasteful. The alternative is accepting the cold start latency and relying only on layer 3 (on-demand warm). For a production deployment, you'd make this configurable.

Performance Optimizations & Trade-offs

Nine targeted optimizations were applied to reduce perceived latency and render load without restructuring the core architecture. Each addresses a specific bottleneck identified through metrics and profiling.

Backend optimizations

Singleton voice model. Previously, every warmModel() and streamChat() call created a new ChatOllama instance. While the LLM connection itself is stateless (Ollama handles model caching), the JavaScript object instantiation and configuration parsing happened redundantly. The singleton pattern (getVoiceModel()) creates the instance once and reuses it, eliminating the overhead. Text chat mode intentionally doesn't use a singleton because it needs different configuration (no numPredict cap).

Parallel database calls. The original code ran four sequential DB queries: findConversation → findAssistant → createMessage → findHistory. But findAssistant and createMessage are independent (they don't depend on each other's result) — so they now run in Promise.all(). This saves one full DB round-trip (typically 1–3ms on localhost, more significant with a remote database).

Correct history direction. The original findByConversationId used ORDER BY createdAt ASC, LIMIT 6 — which returns the oldest 6 messages in the conversation. For a 50-message conversation, this misses all recent context. The new findRecentByConversationId queries DESC, LIMIT 6 and reverses the result, always returning the most recent 6 in chronological order. This is a correctness fix as much as an optimization.

Token batching. At 3.6 tokens/sec, emitting each token as a separate Socket.IO event means ~3.6 events per second. Each event carries framing overhead (event name, JSON encoding, WebSocket frame). The 80ms buffer collects roughly 0.3 tokens per flush on average, batching them into a single string. The flush timer is trailing-edge: it fires 80ms after the first unbatched token arrives. On stream completion or error, the buffer is force-flushed to ensure no tokens are lost.

Frontend optimizations

Notify throttle. The VoiceSession's notify() method triggers a React snapshot update. During active streaming, addToken() calls notify on every token, and the volume analyser calls it at 60fps. throttledNotify() coalesces these: the first call goes through immediately, then a 50ms timer suppresses subsequent calls. If any notify was pending when the timer fires, one final notify is issued. This reduces React re-renders from potentially 60+/sec to ~20/sec without any perceivable delay.

Volume change threshold. The audio analyser computes volume at 60fps, but most frames produce nearly identical values (especially in quiet environments). A threshold of 0.02 means: if the volume hasn't changed by more than 2% since the last notification, skip the re-render entirely. This eliminates roughly 60% of analyser-driven renders.

Adaptive silence timeout. The silence timer that triggers message submission uses two thresholds: 1200ms for the first turn (the user is forming their initial thought and may pause), 800ms for follow-up turns (the conversation is flowing and faster turn-taking is expected). The heuristic is simple: if aiResponse is non-empty, the AI has spoken before, so this is a follow-up.

handleDone safety net. Browser TTS is unreliable — onend callbacks sometimes silently fail (known Chromium issue with certain voices or rapid queue changes). If this happens, the system gets stuck in SPEAKING state forever. A 10-second timer in handleDone() forces a return to LISTENING if TTS callbacks haven't fired. The timer is cleared if the normal path completes, and also cleared when a new turn starts (setProcessing()).

14

Error Handling & Edge Cases

The voice system handles several failure modes:

Microphone denied. If getUserMedia fails (user clicks "Block"), the start() method catches the error, sets this.error = "Microphone access required.", and transitions to ERROR state. The overlay shows the error message and a "Try Again" button. If the recognition itself gets a not-allowed error event, the same path triggers.

Browser not supported. The constructor checks for SpeechRecognition and speechSynthesis on window. If either is missing, isSupported is set to false. The overlay renders a dedicated "Voice Chat Not Supported" screen with a close button — no mic request is made, no socket events fire.

Socket errors and AI failures. The ai_error event handler calls session.handleError(message), which sets the error message and transitions to ERROR state. This covers database failures, Ollama being unreachable, model loading errors, and inference failures. The user sees the specific error message and can retry.

Abort and cancellation. When the user closes the overlay during an active stream, stop() calls cleanup() which tears down all resources (mic, audio context, recognition, TTS). On the backend, the disconnect handler fires currentAbort.abort(), which sets the signal.aborted flag. The stream loop checks this flag on each token and breaks out. The catch clause in streamChat silently swallows aborted errors.

StrictMode double-mount. As discussed in section 03, an AbortController per start() call ensures the first mount's async operations are cancelled when the second mount begins. The getUserMedia promise checks abort.signal.aborted on resolution and stops tracks if the mount was torn down.

TTS onend never fires. The 10-second safety timer in handleDone() catches this. Additionally, TTS onerror handlers ignore "canceled" errors (which are expected when we call speechSynthesis.cancel() deliberately) but handle other errors by checking the stream completion state and returning to listening if appropriate.

SpeechRecognition auto-stops. Chrome's continuous recognition periodically restarts internally. The onend handler restarts it automatically while in LISTENING state. The try-catch around rec.start() handles the race condition where the engine is already starting.

Observability & Metrics

Both the server and client instrument key timing metrics for performance analysis. All log entries are prefixed with [voice-metrics] for easy filtering.

Server-side metrics (ChatService.ts)

A timestamp t0 is recorded at the start of streamChat(). The first token logs TTFT (Time to First Token) — the elapsed time from request receipt to first LLM output. This includes database queries, prompt construction, and Ollama's initial processing. After the stream completes, the total elapsed time, token count, and tokens-per-second are logged.

A turnStartRef timestamp is recorded when the user message is emitted. The first ai_token event logs client-TTFT — which includes server TTFT plus network round-trip plus token batching delay (up to 80ms). The ai_done event logs the total turn-duration — the wall-clock time from sending the message to receiving the stream completion signal.
